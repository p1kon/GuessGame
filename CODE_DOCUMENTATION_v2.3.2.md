## 1. Какую задачу решает система

Пользователь мысленно выбирает 0 либо 1. Компьютер прогнозирует бит **до раскрытия ответа**, сравнивает прогноз с результатом и обновляет состояние. Задача — исследовать, можно ли ловить закономерности человеческой последовательности и адаптироваться, когда игрок сознательно меняет способ выбора, чтобы обыграть алгоритм.

Виртуальный игрок ИНР v0.2 нужен не для замены человека, а как **воспроизводимый тестовый противник**, способный порождать серии, переключения, временное чередование и реакции на прошлые угадывания компьютера. При проектировании ИНР мы ориентировались на описанные пользователем привычки, **не претендуя на универсальную модель психики**.

В версии 2.3 исследование переключается с совершенствования виртуального игрока на сравнение способов **агрегирования одного и того же набора из 16 предсказателей**. Главный вопрос — насколько быстро и устойчиво ансамбль приспосабливается к изменяющемуся игроку.

### Жёсткие исследовательские ограничения

1. Текущий бит выбирается до прогнозирования; утечка будущего запрещена.
2. Виртуальный игрок использует только **прошлые бинарные прогнозы и результаты**; внутренние веса и текущий прогноз ему не передаются.
3. Психологическая модель ИНР v0.2 и её восемь параметров не меняются в этом релизе.
4. Все 16 базовых предсказателей, PPM, CTW-подобная модель, SGD-мета-модель, их обновления и **эталонный** Fixed-Share Hedge сохраняются.
5. В лаборатории каждая конфигурация имеет отдельные экземпляры обеих моделей. Искусственные ходы никогда не попадают в ручное состояние.
6. Генератор случайных чисел не используется ни для выбора виртуального бита, ни как скрытый способ усложнить соперника.

## 3. Жизненный цикл одного хода

### В ручном режиме

1. Пользователь заранее загадывает бит и нажимает **«Угадай»**.
2. `manualEngine.predict(now, visible)` собирает доступный до ответа контекст, считает вероятности экспертов и смешивает их эталонными весами.
3. `snapshot` фиксирует `guess`, `prob1`, все вероятности экспертов, признаки для SGD, копию текущих весов и время прогноза.
4. При подтверждении пользователь вводит фактический бит. `manualEngine.update(actual,snapshot)` **учится по ранее зафиксированному снимку**, а не пересчитывает «прошлый» прогноз из нового состояния.
5. Обновляются Fixed-Share Hedge, SGD, CTW, быстродействующие счётчики, история битов, прогнозы, лог прогнозов, PPM и время сессии.
6. Ручной интерфейс сохраняет состояние в `localStorage`.

Факт выбора до прогноза — предпосылка, которую соблюдает пользователь; интерфейс не способен проверить, не изменил ли он мысленно ответ после просмотра прогноза. **Слепой режим** скрывает прогноз до подтверждения и уменьшает реактивное влияние видимого ответа.

### В лаборатории

```js
// Схематическое представление, имена действительных методов сохранены.
const decision = player.choose();        // бит уже зафиксирован
const forecast = predictor.predict(t,false);
predictor.update(decision.bit,forecast,{source:'simulated'});
const feedback = player.feedback(forecast.guess);
log(decision,forecast,feedback);
```

Текущий прогноз не попадает в `VirtualPlayer.choose()`. Следующая попытка учитывает только предыдущую обратную связь. При смене G извне расписание применяется **до** очередного `choose()`.

## 4. Модель данных и инварианты

### Ручное состояние `PredictorEngine.state`

| Поле | Смысл |
|---|---|
| `history` | Подтверждённые биты (0/1) |
| `moveTimes` | Время каждого хода в миллисекундах Unix или `null` для старых ходов |
| `predictions` | Исторический бинарный прогноз на каждый ход или `null` |
| `forecastLog` | Полный журнал фактически показанных прогнозов, P(1) и времени; в RAM для новых ходов также подробные снимки 16 экспертов; в localStorage эти 32 значения прорежены |
| `weights` | 16 базовых весов эталонного Hedge |
| `ppm`, `ctw`, `sgd` | Обучаемые внутренние состояния соответствующих экспертов |
| `correct`, `total` | Реальные сохранённые результаты ручной игры |
| `lastPrediction`, `blindMode`, `startedAt` | Текущий контекст и настройки |
| `schemaVersion`, `algorithmVersion` | Схема 2.1 и метка версии приложения |

Основные инварианты: длины `history`, `moveTimes`, `predictions` и `forecastLog` согласованы после загрузки; биты только 0/1; веса неотрицательны; их сумма равна 16; верхний предел каждого веса — 5 (после нормировки). `correct` относится к реально сохранённым прогнозам, **не к результатам задним числом пересчитанного replay**.

`emptyState()` создаёт чистое состояние. `validatePayload()` проверяет JSON и вложенные структуры. `hydrateState()` восстанавливает модели; если старый JSON не содержит полного журнала, заполняет недостающие сведения честными `null` и пометкой `legacy`. `serializable()` переводит `Map` из PPM и CTW в массивы пар для JSON. `load()`, `save()` и `writeWithBackup()` работают исключительно в ручном режиме.

`localStorage` использует прежний ключ `guessGameState_v1`, а резервная версия хранится в `guessGameState_v1_backup`. Копия обновляется предыдущим валидным состоянием перед записью нового. Невалидная запись сначала переносится в нумеруемый карантин; при невозможности создать подтверждённую копию перезапись запрещена. Сохраняемый JSON сокращает только подробные диагностические поля отдельных ходов (`expertProbs`/`expertWeights`) до одного снимка на 50 ходов плюс последний, не удаляя биты, фактически показанные прогнозы, P(1) и времена. Это не полноценная система версионных бэкапов. **Сохраняйте ручные JSON-экспорты отдельно и экспортируйте полный журнал до закрытия текущей вкладки, если нужны свежие поминутные экспертные снимки.**

### Разница между ручными и лабораторными файлами

Ручной экспорт представляет состояние модели, пригодное для импорта в игру. Экспорт лаборатории имеет отдельную форму (`GuessGameExperiment`, `GuessGameExperimentComparison`, `GuessGameBenchmarkSuite`), содержит искусственные ходы и **не импортируется в ручную историю**. Это намеренно: смешивать реальные и искусственные данные нельзя.

## 5. Все 16 предсказателей

Каждый возвращает оценку `p_i = P(следующий бит равен 1)` — не обязательно хорошо откалиброванную. Результат приводится к безопасному диапазону, и эксперты голосуют вероятностями, не бинарными решениями.

| Эксперт | История / метод | Какую структуру ловит и почему он нужен |
|---|---|---|
| `global` | Глобальная доля единиц | Общая асимметрия 0/1; контрольный простейший эксперт |
| `recent10` | Последние 10 бит | Быстрый локальный сдвиг частоты |
| `markov1` | Глобальный контекст из 1 бита | Повтор/чередование в зависимости от последнего бита |
| `markov2` | Глобальный контекст из 2 битов | Серии длины 2 и короткие комбинации |
| `markov3` | Текущая сессия, контекст из 3 битов | Более длинные зависимости без ложных склеек сеансов |
| `opposite` | Последний бит в сессии | Заданная склонность к чередованию |
| `streak` | Длина текущей сессионной серии | Заданная эвристика продолжения серии |
| `pattern` | Глобальный поиск повторяющегося суффикса до 6 битов | Повторные мотивы без явной параметрической модели |
| `ppm` | Глобальные контексты 0–4 | Смешивание длин контекстов и escape-переходы |
| `anti` | Предыдущее предсказание | Реакция «играть против последней догадки» |
| `response` | Предыдущее предсказание и предыдущий реальный бит | Более тонкая реакция на компьютер |
| `runLength` | Глобальная статистика продолжения серии по длинам 1–8+ | Изучаемое, а не заранее заданное завершение серии |
| `ewma20` | Все ходы, экспоненциальное затухание | Среднесрочное смещение частоты |
| `ewma50` | Аналогично, более медленное затухание | Долговременные изменения относительно `recent10` |
| `ctw` | Глобальные контексты 0–5 | Контекстное смешивание с показателем надёжности и прошлой пользы |
| `sgdMeta` | Голоса остальных 15 и четыре дополнительных признака | Нелинейная по итоговой вероятности метакомбинация через логистическую регрессию |

**Почему именно 16?** Это наследие экспериментальной эволюции 2.0–2.2: эксперты покрывают разные источники закономерностей, в том числе реакцию на собственные прогнозы модели. Состав здесь **не отбирался заново** и не претендует на математически минимальный набор; он заморожен для честного исследования агрегаторов.

### Отдельные формулы и ограничения

**Марков:** `(ones+1)/(total+2)` — сглаживание Лапласа. При недостаточной статистике результат близок к 0.5.

**`opposite`:** после 0 выдаёт `P(1)=0.85`, после 1 — `0.15`.

**`streak`:** уверенность продолжить `min(0.5+0.08*длина_серии,0.9)`.

**`pattern`:** самый длинный суффикс до 6 битов, который встретился прежде минимум 5 раз; если нет — 0.5.

**`runLength`:** оценивает вероятность продолжения по накопленным наблюдениям, группирует длины 8 и более; если наблюдений для группы меньше 5 — 0.5.

**EWMA:** `p ← p + α(x−p)`, где `α = 1−0.5^(1/halfLife)` и `halfLife` равен 20 либо 50 ходам.

**PPM:** использует уровни контекста 0–4. При найденном контексте `p_here = ones/(total+1)`, `p_escape = 1/(total+1)`, `p = p_here + p_escape*p_lower`. Затем вероятность сжимается к 0.5, сильнее на краях (`TEMP_EDGE=2`, `TEMP_MID=1.5`). В этой реализации это прикладной PPM-подобный алгоритм, не претензия на идеально стандартизованную реализацию компрессора PPM-A.

**CTW-подобная модель:** глубина 0–5, псевдосчётчики `α=0.5`, надёжность контекста `total/(total+15)` (для глубины 0 берётся 1), штраф глубины `log(0.85)` на уровень, скользящее преимущество по log loss со скоростью 0.05 и масштабом 4. Это **не канонический академический CTW**, а практическое контекстное смешивание.

**SGD:** 20 признаков (bias + 15 базовых вероятностей + последний фактический бит, последний прогноз, последнее попадание, нормированная длина сессии). `lr=0.05/(1+t/500)`, `L2=0.0005`, вероятности обрезаются до `[0.02,0.98]`. SGD обновляется по фактическому исходу **после** формирования прогноза; его вес в общем ансамбле обновляется обычным Hedge.

**Ограничение.** Эти эксперты обучаются на реальной истории как на данных одного онлайн-процесса. При взаимодействии с живым человеком сама история может зависеть от показанных прогнозов; повторная проверка по старым битам не воспроизводит первоначальную игру.

## 6. Эталонный Fixed-Share Hedge — без изменения

Для каждого эксперта `i` с вероятностью `p_i` и исходом `y∈{0,1}` линейная потеря:

```text
loss_i = y==1 ? (1-p_i) : p_i
w'_i = w_i * exp(-η*loss_i)
η = 0.3
```

Затем веса нормируются к сумме 16, с строгим потолком 5, и применяется Fixed-Share:

```text
w''_i = (1-share)*w'_i + share
share = 0.02
```

После ещё одной нормировки с потолком расчётная итоговая вероятность:

```text
P(1) = sum_i(w_i * p_i) / sum_i(w_i)
guess = P(1) >= 0.5 ? 1 : 0
```

**Обоснование решения.** Мультипликативные веса переводят качество прошлых предсказателей в их влияние. Fixed-Share не позволяет отстающему эксперту навсегда исчезнуть: когда человек меняет стратегию, ранее плохая модель может снова стать полезной. Потолок 5 ограничивает доминирование одного предсказателя. Конкретные значения η и share — инженерные гипотезы, а не доказанные оптимумы.

Эталонные функции `predictFrom`, `applyUpdate`, 16 экспертов и обучение их внутренних моделей оставлены без изменения. В ручной игре `PredictorEngine` **всегда** создаётся с режимом `baseline`.

## 7. Новые альтернативы агрегирования

Важное различие: **предсказатель ≠ агрегатор**. 16 предсказателей генерируют свои `p_i`; агрегатор решает, как смешивать их и как менять веса.

### 7.1. Скорости

| Режим | η | Fixed-Share |
|---|---:|---:|
| `baseline` | 0.30 | 0.02 |
| `slow` | 0.08 | 0.01 |
| `fast` | 0.90 | 0.06 |
| Внутренние головы `multi` | 0.08 / 0.30 / 0.90 | 0.01 / 0.02 / 0.06 |

`slow` меняет относительные веса осторожнее, `fast` сильнее реагирует на новые ошибки. Больший share у быстрого режима уменьшает инерцию веса ранее неудачных экспертов. Значения выбраны как **экспериментально различающиеся масштабы вокруг η=0.30**, а не подогнаны под тестовую батарею.

Каждая альтернатива реализована классом `MultiRateHedge`, который хранит собственные наборы весов; её обучение производится из тех же снимков экспертных вероятностей. Ограничение суммы 16 и потолка 5 сохраняется в каждом наборе.

### 7.2. Три скорости (multi)

Каждая из трёх «голов» независимо смешивает голоса 16 экспертов:

```text
p_slow, p_medium, p_fast
```

Итоговое смешивание:

```text
p_mix = a_slow*p_slow + a_medium*p_medium + a_fast*p_fast
sum(a_i)=1
```

Внешние мета-веса тоже учатся по линейной потере **на собственных предварительно сохранённых прогнозах голов**:

```text
u_i = a_i * exp(-0.7 * loss(p_i,y))
a_i(new) = 0.975 * u_i/sum(u) + 0.025/3
```

Потом внутренние головы обновляют свои экспертные веса. Это двухуровневое онлайн-обучение: сначала эксперты в каждой голове, затем выбор временного масштаба.

**Почему две ступени?** Если эффективность одной скорости меняется со стратегией игрока, внешний слой потенциально способен перераспределять доверие между скоростями. Однако на практике он тоже может переобучиться или запаздывать, а усреднение голов может размывать сильный сигнал — поэтому это только кандидат, не улучшение по определению.

`PredictorEngine` у экспериментальных режимов продолжает обновлять эталонные `state.weights` **параллельно как неиспользуемую для финального прогноза контрольную ветвь**. Это сохраняет обратную совместимость объекта состояния и неизменность работы экспертных моделей. Собственные веса альтернативных агрегаторов живут отдельно в `experimental` и не сохраняются в ручном `localStorage`. Экспорт лаборатории содержит их трассу и мета-веса; **ручная игра альтернативных режимов не включает**.

**Оговорка при обученном старте:** альтернативы инициализируются существующими весами `state.weights` из копии ручной истории, но их индивидуальные прошлые траектории на этой истории не были переобучены заново. Поэтому такие прогоны исследуют адаптацию *после общего начального состояния*, а не полноценное сравнение исторически обученных разными алгоритмами предсказателей. Для чистой базы использовать `fresh`.

## 8. Виртуальный игрок ИНР v0.2 — заморожен

ИНР v0.2 представляет **восемь настраиваемых параметров** и динамическое внутреннее состояние. В релизе 2.3 его код не менялся, кроме того, что `SimulationRunner` может **извне** сменить G на известной границе экспериментального блока.

| Параметр | Начальное значение | Допустимый диапазон | Психологическая гипотеза |
|---|---:|---:|---|
| `I` | 0.70 | 0…1 | Инерция продолжения битовой серии |
| `S` | 0.80 | 0…1 | Насыщение повторениями |
| `M` | 5 | 1…20 | Доступный объём краткой истории |
| `C` | 0.65 | 0…1 | Контроль над автоматическими действиями |
| `G` | −1 | −1…+1 | Против компьютера / нейтрально / за компьютер |
| `Q` | 0.50 | 0…1 | Исследование менее привычных вариантов |
| `E` | 0.60 | 0…1 | Эмоциональная чувствительность |
| `D` | 0.70 | 0…1 | Сохранение эмоционального состояния |

Кроме параметров у игрока меняются `V` (валентность −1…1), `A` (активация 0…1), длина текущей серии `k`, последний бит и ограниченная память последней сессии. Параметры задаются пользователем в UI; обычно они постоянны на протяжении эксперимента. В сценариях `goalSwitch` **внешне** переключается только G. Психологические свойства и формулы остаются неизменными.

### 8.1. Внутренние наблюдения

`recentRepeats()` определяет долю повторений в последних M переходах. `estimateContinuation(k,bit)` оценивает, насколько компьютер по субъективной модели игрока ожидает продолжения серии, по **прошлым** наблюдаемым прогнозам. Сходство контекста учитывает тот же бит (0/1), длину серии и давность эпизода; неизвестные ожидания сглаживаются к 0.5.

`perceivedThreat()` оценивает частые успехи компьютера по последним `min(M,5)` ходам с большим весом недавних. Она действует как защитная реакция только при G<0. `exploreNovelty()` выясняет, какое действие (продолжить или переключиться) реже предпринималось в сходном контексте.

### 8.2. Алгоритм принятия решения

В обозначениях программы:

```text
Cbase = clip(C*(1 + .5*A - .25*abs(V)), 0, 1)
agency = Cbase/(Cbase+.15)   // либо 0 при Cbase=0
oppose = max(0,-G)
prolong = oppose*agency*(1-q)

Ieff = clip(I + .30*V - .28*A - .95*threat*agency + .18*prolong, 0, 1)
Seff = clip(S*(1 + .35*A + .65*threat*agency - 1.15*prolong - .15*V), .06, 1)

automatic = 2*Ieff - 2*Seff*(k-1) + .4*S*(1-2*f)
reflexive = 2.5*agency*G*(2*q-1)
exploration = -1.8*agency*Q*novelty
alternation = -.95*threat*agency*(k==1 ? 1 : .35)
impulse = automatic + reflexive + exploration + alternation

bit = impulse >= 0 ? lastBit : 1-lastBit
```

Первый бит новой сессии берётся из внешней настройки. **Длина будущей серии заранее не планируется**; решение принимается на каждом ходе. При высоких успехах компьютера угроза может временно ослабить инерцию и поддержать чередование. При предполагаемом ожидании завершения серии сознательный контроль может продлить её до четырёх и более ходов. Все формулы фиксированы и детерминированы.

### 8.3. Эмоциональное обновление

После раскрытия прогноза вычисляются соревновательная оценка `rGoal = G*(2*hit−1)` и оценка предвидения компьютера `rInsight = clip(1−4*(pExpectedBit1−guess)^2,−1,1)`. Их смесь:

```text
reward = (1-Q)*rGoal + Q*rInsight
expected = среднее reward за последние M ходов сессии (или 0)
Vnew = clip(D*V + (1-D)*E*reward, -1, 1)
Anew = clip(D*A + (1-D)*E*abs(reward-expected), 0, 1)
```

Если E=0, V=A=0. Они не назначают конкретный бит напрямую, но через Ieff/Seff/Cbase влияют на следующий выбор. **Это инженерные гипотезы об аффекте**, а не установленная нейропсихологическая модель эмоций.

### 8.4. Начало новой сессии

`beginSession()` обнуляет недавние наблюдения, V и A, последнюю серию и ожидающий ход. Параметры I,S,M,C,G,Q,E,D сохраняются; стартовый бит задаётся извне. При смене G посреди сессии всё прочее состояние **не обнуляется**: это позволяет исследовать именно реакцию на новую цель.

## 9. Сеансы, виртуальное время и изоляция

`SimulationRunner` поддерживает `turns` (от 1 до 10 000), `sessionSize`, стартовый бит 0/1 или чередование начальных битов по сеансам. Между искусственными ходами проходит 2000 мс виртуального времени; между сеансами добавляется 600000 мс (10 минут). Время передаётся предсказателю, чтобы тот определял новые сессии тем же механизмом, что и при ручной игре.

`new SimulationRunner({params,turns,sessionSize,startState,initialBit,alternateStart,aggregator,goalSchedule})` создаёт **отдельные** объекты обеих моделей.

Начальное состояние предсказателя:

- `fresh` — чистое `emptyState()` без прежних ходов;
- `trained` — сериализованная и заново гидратированная **копия** текущей ручной истории, включая историю и статистику, но без общих изменяемых `Map`.

Сохранение результатов симуляции в `localStorage` вручную **не выполняется**. При `trained` новый предсказатель может накапливать фиктивные ходы в своей копии состояния, но ручная статистика не меняется.

### Внешние изменения G

`goalSchedule` — массив объектов `{at:номер_хода_с_1,g:новая_цель}`. Например:

```js
[{at:1,g:0},{at:201,g:-1},{at:401,g:0}]
```

В лаборатории расписание устанавливается для специальных сценариев на приблизительных третях длины опыта; если длина не кратна трём, блоки отличаются на несколько ходов. Это **интервенция экспериментатора**, а не внутренняя обучаемая цель игрока. Смена G не обязана совпадать с границей сеанса.

## 10. Исследовательские сценарии и методика сравнения

`BENCHMARK_PRESETS` — заранее заданная батарея, воспроизводимая с параметрами пользователя и фиксированными корректировками сценария. При запуске «Батарея: разработка» сравниваются все четыре агрегатора в шести условиях:

| ID | Условие | Изменение исходной конфигурации |
|---|---|---|
| `anti` | Против компьютера | G=−1 |
| `neutral` | Нейтрально | G=0 |
| `cooperate` | За компьютер | G=+1 |
| `shortMemory` | Короткая память | G=−1, M=3 |
| `noEmotion` | Без эмоций | G=−1, E=0 |
| `switchGoal` | Внешняя смена цели | блоки G=0, −1, 0 |

«Резервные сценарии» запускают два ранее объявленных варианта параметров: `heldoutA` (другая конфигурация инерции, насыщения, памяти, контроля, интереса и эмоций), `heldoutB` (другая конфигурация плюс внешнее переключение G). Их фактические константы находятся в `BENCHMARK_PRESETS` — намеренно доступны для проверки. **Резерв не считается слепым статистическим holdout**, если по нему многократно подбирают модель. Для добросовестного сравнения его нужно запускать после фиксации кандидатов.

### Что именно сравнивается

В интерфейсе пакетная батарея ограничена **2000 ходами на сценарий**, чтобы не запускать случайно десятки очень длинных прогонов; отдельный `SimulationRunner` и одиночная игра допускают 10 000.

Каждый агрегатор **взаимодействует с собственной копией** виртуального игрока, отвечающего на предыдущие прогнозы этого агрегатора. Поэтому разные агрегаторы могут получить разные цепочки битов.

Это корректно для вопроса **«как работает замкнутая система предсказатель–адаптивный игрок?»**, но не даёт идеально контролируемого парного сравнения на одинаковом входе. Если потребуется парное off-policy-сравнение на замороженной последовательности, его следует реализовывать отдельно и снабдить оговоркой, что такая история не учитывает реакцию игрока на альтернативные прогнозы.

Различия на коротких отрезках и в единственном детерминированном прогоне нельзя автоматически считать статистически значимыми. Качество кандидатов следует проверять в нескольких заранее зафиксированных условиях и в конечном счёте на новых человеческих данных.

## 11. Метрики — определения и интерпретация

| Метрика | Формула | Интерпретация |
|---|---|---|
| Accuracy | `sum(guess==bit)/N` | Угаданные биты |
| Local 50/100 | Точность на последнем непустом окне длины до 50/100 | Текущее качество, чувствительно к колебаниям |
| Brier | `sum((p1-bit)²)/N` | Вероятностная точность; меньше лучше |
| Повторы | Доля продолжений серии среди ходов, где есть предыдущий бит в той же сессии | Характер процесса выбора |
| Серии 1,2,3,4+ | Завершённые серии внутри сеансов | Психологическая форма поведения |
| Просадка | `accuracy(pre50) − accuracy(post50)` | Падение после внешней смены G; отрицательная просадка = рост точности |
| Восстановление | Первое **полное** скользящее окно 50 после смены с `acc >= pre50 − 0.05` | Скорость возвращения к почти исходной точности |
| Ошибки после смены | Число ошибок в первых 50 ходах после интервенции | Цена адаптации |

Правило восстановления существенно ограничено: **следующая интервенция G завершает окно наблюдения предыдущей**. Если порог не достигнут до следующей смены, `recoveryMoves=null` и интерфейс пишет «Не зафиксировано». Слишком короткий период также не позволяет оценить восстановление. Порог в 5 процентных пунктов — рабочее соглашение для исследовательского стенда; не психологическая или математическая константа.

Сводные показатели батареи вычисляют точность по всем ходам заданных сценариев и средний Brier. Кооперативные случаи могут резко повышать общую цифру и скрывать слабость модели в соревновательном режиме. Поэтому сравнивать нужно по сценариям и особенно по *адаптации после смены цели*, а не только по агрегированному рейтингу.

### Трасса весов

Для каждого одиночного эксперимента сохраняются 16 **эффективных** весов с периодом 10 ходов, плюс снимки в момент смены G, на первом и последнем ходах. Базовый режим показывает собственные Fixed-Share веса. `slow` и `fast` показывают веса соответствующей одной головы. `multi` показывает **взвешенную смесь трёх наборов** по текущим внешним мета-весам, а также итоговые мета-веса скоростей.

График выводит пять экспертов, которые имеют наибольший вес в конце прогона; это удобная диагностика, но не полный анализ всех 16. Полный набор снимков сохраняется в экспортируемом журнале `weightTrace`.

## 13. Техническая проверка и регрессионные результаты

### Как проверять сохранение эталона

1. Загрузить один и тот же старый JSON в 2.2/ИНР 0.2 и 2.3.
2. Создать `PredictorEngine` из одинаковой гидратированной копии состояния.
3. Последовательно вычислить 32 прогноза, раскрывая одинаковые биты; сравнивать **покадрово** `guess`, `prob1`, после каждого шага `weights` и состояние `sgd`.
4. Повторить эталонную симуляцию 600 ходов с фиксированными параметрами ИНР; сравнить все 600 битов, прогнозы, вероятности, V и финальные веса.
5. Проверить UI и что `state.total` ручной истории после лабораторных запусков не изменился.

Эти проверки **выполнены** при подготовке 2.3. Эталонный режим совпал точно; браузерные тесты режимов, сценариев разработки и резерва завершились без ошибок JS. В сценарии старта из копии исторических 1200 ходов после 210 искусственных шагов изменялась лишь копия предсказателя (до 1410).

Эти сводные цифры **не показывают убедительного победителя**: различия малы, сценарии детерминированы и не независимы статистически, а лёгкие кооперативные условия имеют существенный вес. В соревновательном сценарии `G=−1` отдельные результаты были: baseline 68.83%, slow 70.67%, fast 68.83%, multi 68.67%. Новые режимы пока только кандидаты для дальнейшего испытания.

## 14. Причины основных проектных решений

**Почему сохраняем 16 экспертов?** Они уже работали на человеческой истории; их замена одновременно с агрегатором сделала бы невозможной интерпретацию изменения точности. Замороженный состав позволяет изолировать экспериментальный фактор.

**Почему ИНР тоже заморожен?** Ранее его математическая модель многократно менялась. Теперь он служит устойчивым тестовым объектом. Допустимо варьировать восемь параметров и внешне менять G, но **не переписывать правило выбора под каждый результат**.

**Почему четыре агрегатора, а не большая нейросеть?** Контрастные η дают простой интерпретируемый тест скорости адаптации с минимальным вмешательством. Трёхскоростная смесь — контролируемое усложнение для проверки, действительно ли разные временные горизонты помогают.

**Почему не запускаем алгоритмы на одинаковой заранее сгенерированной истории?** Потому что цель проекта — реактивный противник; его следующий бит зависит от прошлых прогнозов конкретной модели. Замороженная история полезна как дополнительный тест статистики, но не является полноценной игрой с адаптивным противником.

**Почему нужны окна 50/100?** Суммарная точность за 10 000 ходов сглаживает кратковременные провалы. Окна фиксируют изменение текущего поведения, хотя слишком короткое окно шумнее общего результата.

**Почему смена G — внешняя?** Это контролируемая интервенция, не новая обучаемая психическая переменная. По ней мы знаем точный момент смены условий и можем объективнее обсуждать адаптацию.

**Почему есть резервная батарея?** Чтобы снизить риск подгонки ко всем заранее видимым настройкам разработки. Но удержанный сценарий действительно контрольный лишь пока его не используют для подбора — в открытом HTML он не скрыт и не защищён от повторных запусков.

**Почему нет внешнего API или робота-кликера?** Внутренние вызовы быстрее, детерминированны и не зависят от задержек UI. При необходимости можно вынести ядро в отдельный JS-модуль и позднее сделать API, не переписывая математические алгоритмы.

## 15. Известные ограничения и честная трактовка

1. ИНР является **моделью описанных привычек конкретного человека**, а не доказанной моделью любой человеческой психики.
2. Все искусственные игры детерминированы; повтор одинакового запуска не создаёт независимую выборку. Для надёжности нужно сравнивать разные условия и проверять на новых человеческих данных.
3. Прогнозы разных агрегаторов меняют будущее поведение игрока, поэтому нет парной независимости наблюдений.
4. Параметры альтернативных Hedge и мета-головы — **экспериментальные настройки**, не оценённые оптимумы.
5. Длинные прогоны могут отражать адаптацию к особенностям ИНР, а не универсально высокую устойчивость к человеческой импровизации.
6. Общее среднее по батарее может быть обманчиво из-за тривиальных кооперативных последовательностей.
7. `recoverMoves=null` может означать отсутствие достижения порога или слишком короткий период до следующей смены G; это не доказательство невозможности восстановления.
8. Альтернативные агрегаторы при импорте ручной истории имеют общий стартовый вектор весов, но не свою полную историческую многоскоростную тренировку.
9. `replay()` на старых битах не восстанавливает реальные старые прогнозы человека и не учитывает, как человек изменил бы поведение при другой модели.
10. Объём `localStorage` конечен; при превышении квоты ручные ходы могут оставаться только в памяти вкладки до экспорта. Диагностические массивы по отдельным ходам в постоянном хранилище разрежены: полный снимок каждые 50 ходов + последний. При перезагрузке недостающие снимки не реконструируются; основной фактический прогноз и P(1) сохраняются. Лабораторный экспорт — скачиваемый файл, не база данных.
11. Приложение не поддерживает синхронизацию между устройствами, совместную работу, серверное хранение или внешние психологические измерения состояния.
12. Коэффициенты ИНР и её `V/A` моделируют **вычислимые переменные**, но не дают доступа к реальным эмоциям человека.

## 16. Рекомендованный следующий научный цикл

1. Зафиксировать исходные версии: **baseline 2.2**, ИНР 0.2 и батарею разработки 2.3.
2. Исследовать характер просадок после смены G у каждого агрегатора, отдельно от общей точности.
3. Отобрать один-два кандидата по заранее установленным критериям без использования резерва.
4. Протестировать выбранных кандидатов на двух резервных сценариях ровно в согласованном виде.
5. Провести свежие раунды игры с человеком (желательно с разделением слепого и видимого режима), чтобы оценить перенос результатов.
6. Только после этого решать, стоит ли добавлять детектор смены стратегии или контекстное смешивание экспертов.

**Итог:** версия 2.3 не пытается «победить человека» заранее выбранной более сложной формулой. Она создаёт условия, в которых можно проверять конкретные объяснимые гипотезы об адаптации ансамбля — сохраняя прежнего предсказателя, прежнего виртуального игрока и полную прослеживаемость экспериментов.

## 17. Пакет исправлений v2.3.2 и причины выбора

### 17.1. Цель инженерного релиза

В отличие от версии 2.3, выпуск 2.3.2 не предлагает новой предсказательной модели. Исходные 16 экспертов, порядок вычислений, Fixed-Share Hedge, альтернативные агрегаторы и виртуальный игрок ИНР v0.2 неизменны. Изменения касаются долговременного хранения, интерфейса ошибок и научной диагностики. Показатели батареи в §13 являются **историческими замерами 2.3.0**, а не новыми независимыми исследованиями 2.3.2.

### 17.2. Три представления одной истории

1. **Оперативное состояние (`state`)** — все фактически выполненные ходы текущего запуска и полные диагностические снимки для новых ходов.
2. **Компактное состояние (`compactForStorage(serializable(state))`)** — та же история и всё необходимое для продолжения обучения, но `expertProbs/expertWeights` для большинства строк удалены. Полные снимки остаются для `i % 50 === 0` и последней строки. Важно: индекс `i` нулевой, то есть сохраняются записи 1, 51, 101 и т. д. и последний ход.
3. **Ручной экспорт (`serializable(state)`)** — полный объём сведений, доступных в оперативной памяти; исторические снимки, уже утраченные при предыдущих перезагрузках, не восстанавливаются.

`compactForStorage` не изменяет исходные объекты `state.forecastLog`: записи клонируются без диагностических полей, а другие поля остаются прежними. `validatePayload` по-прежнему проверяет `forecastLog` даже при отсутствии необязательных диагностических ключей. Введённая схема не меняет `SCHEMA_VERSION = 2.1` и читается прежними версиями.

**Почему не хранить только последнее состояние модели?** Для статистики и будущего исследования нужны реальные биты, прогнозы и времена каждого хода. Это невосполнимые измерения. Напротив, снимки внутренних голосов и весов частично диагностические; поэтому они имеют меньший приоритет в условиях ограниченной браузерной квоты.

**Почему не IndexedDB сейчас?** Асинхронная транзакционная база решила бы вопрос объёма, но потребовала бы изменения жизненного цикла сохранения, миграции и дополнительного тестирования. Для замороженной исследовательской серии предпочтён компактный обратносовместимый `localStorage` и файловый экспорт.

### 17.3. Fail-closed карантин

`writeWithBackup(payload)` принимает готовый JSON-совместимый объект и вызывает `JSON.stringify`, затем читает старый основной ключ. Если прежнее содержимое валидно, оно записывается в `_backup` **до** новой основной записи. Если оно невалидно, функция `protectCorruptRecord(raw)` ищет первую свободную карантинную ячейку, либо уже существующую идентичную копию. Новое содержимое записывается только после подтверждения копии.

Если `setItem()` карантина или резервной копии выдаёт `QuotaExceededError`, исключение не подавляется и основная запись остаётся неизменной. Таким образом, **исправление R1 не зависит от того, свободен ли первый карантинный ключ**.

Функция `downloadStorageRecovery()` даёт скачать исходные строки ключей `guessGameState_v1`, `_backup`, `_quarantine` и индексированных карантинов. Экспорт помечен `format: GuessGameStorageRecovery`: он предназначен для восстановления человеком и **не проходит** обычный импорт.

### 17.4. Сбой сохранения ≠ сбой вычисления

Ранее `update(actual, snapshot)` одновременно изменял `PredictorEngine` и вызывал `save()`, а исключение от записи прерывало UI с уже изменённой памятью и несброшенным `currentForecast`. Теперь `manualEngine.update()` завершается независимо; затем `persistOrMarkUnsaved()` пытается сохранить и ловит только ошибку хранилища. При ошибке `saveError` показывается в `#persistenceNotice`, а `lastSavedTotal` остаётся прежним.

Игрок может продолжать ход за ходом. Но данные **не защищены от закрытия вкладки**, пока запись не удастся; UI предлагает скачивание текущего JSON и повторное сохранение. После успешной записи `lastSavedTotal` обновляется, а предупреждение исчезает, если нет отдельного уведомления о повреждённом прежнем состоянии.

Сброс статистики выполнен транзакционно: формируется `next = emptyState()`, сначала вызывается `writeWithBackup(compactForStorage(serializable(next)))`, и только при успехе заменяются `state` и `manualEngine`. При неудаче прежние данные остаются и в памяти, и в хранилище.

**Принцип:** не пытаться «откатить» сложную последовательность обновлений SGD, PPM и CTW. Ошибка диска не должна становиться ложной ошибкой машинного обучения.

### 17.5. Диагностика и 16 экспертов

`replay(..., {collectBenchmark:true})` теперь собирает walk-forward-метрики для `ensemble`, `always0`, `always1` и **всех** имён из `PREDICTORS`. При `renderBenchmark()` делается копия `benchmarkHistory` и `benchmarkTimes`: абляции через `setTimeout` работают с одними входами, даже если игрок нажал кнопку очередного ручного хода. Значения экспертов не изменяются, меняется только полнота отображения результатов.

### 17.6. Границы совместимости и обновления

- Состояния и исторические JSON из v2.2/v2.3/v2.3.1 читаются без миграции схемы; при импорте сохраняются все реальные ходы и их показанные прогнозы.
- Полная диагностическая история из старого файла продолжает существовать в RAM до закрытия вкладки, но при первой новой персистентной записи будет прорежена. **Сохраните исходный файл старой версии как архив, если эта детализация важна.**
- Карантинные ключи не удаляются автоматически, чтобы не уничтожить потенциально восстанавливаемую информацию; их объём тоже расходует квоту браузера.
- Все тесты и приоритеты дополнительных улучшений перечислены в `RELEASE_DECISIONS_v2.3.2.md`.
- Для научных экспериментов фиксируются SHA-256 артефактов; любые последующие правки требуют новой версии.
