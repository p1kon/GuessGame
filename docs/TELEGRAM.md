# Закрытый Telegram-адаптер: подготовка этапа 3

Дата: 2026-11-14. Протокол сессий: `telegram-private-1`. Автотесты используют искусственные обновления. Владелец отдельно проверил настоящий запуск, личную игру и сохранение состояния после перезапуска. Токен и Telegram ID остаются в локальной конфигурации. Она предназначена для личного теста владельцем, а не для публичного набора участников.

## Первый запуск в PowerShell

Бот и числовой Telegram ID у владельца уже есть. В корне проекта создан игнорируемый `.env`. Откройте его и заполните только две пустые строки: `TELEGRAM_BOT_TOKEN` и `TELEGRAM_ALLOWED_USER_IDS`. В список доступа для первого теста внесите только свой числовой ID. Токен не отправляйте в чат или GitHub.

```powershell
cd C:\Users\Павел\GuessGame
notepad .env
npm.cmd run telegram:check
npm.cmd run telegram:start
```

Если `.env` отсутствует на другом компьютере, скопируйте `.env.example`, заполните также текст и версию согласия. Проверка `telegram:check` не использует сеть, не создаёт БД и не проверяет действительность токена. Запуск проверяет `getMe` и существующий webhook; активный webhook автоматически не удаляется. Данные хранятся в `private/telegram.sqlite`.

После сообщения о запуске откройте личный чат со своим ботом и отправьте `/start`. Прочитайте условия и подтвердите согласие, выберите видимый или слепой режим. Перед «Угадай» мысленно выберите 0/1, после фиксации прогноза нажмите свой бит. `Ctrl+C` останавливает процесс. Пока компьютер или процесс выключен, бот не отвечает. Облачное размещение этим этапом не настраивалось.

Если видите `POLLER_ALREADY_RUNNING`, остановите второй экземпляр. После аварийного завершения блокировка истечёт через две минуты. `TELEGRAM_API_401` означает ошибку авторизации токена; `409` — конфликт polling/webhook или другого процесса. Сообщение `WEBHOOK_ACTIVE` требует отдельно разобраться с уже настроенным webhook. Бот не меняет настройки существующих интеграций автоматически.

## Команды и ограничения доступа

| Команда | Действие |
|---|---|
| `/start`, `/help` | Условия участия и выбор режима |
| `/resume` | Восстановить ожидающий ход или кнопку следующего; отменить запрос удаления |
| `/stats` | Число завершённых ходов и угадываний |
| `/export` | Собственный JSON без Telegram ID; при скрытом незавершённом ходе сначала требуется ответ |
| `/delete` | Запрос подтверждения удаления своей истории и модели |

Бот обрабатывает только личные чаты разрешённых пользователей, сверяет `from.id` с `chat.id`. Callback должен прийти от сообщения этого бота. Идентификатор участника выбирается из приватной таблицы связи, а не из callback. Владение сессией и ходом дополнительно проверяет GameService. Имена, username, телефоны и исходный JSON обновлений не сохраняются. Список доступа в `.env` — отдельная конфигурация владельца.

Согласие запрашивается до создания модели. Версия, полный текст и хеш условий сохраняются отдельно, вместе с временем принятия участником. Изменение текста или версии требует повторного согласия; экспорт и удаление остаются доступны. Предварительный текст `.env` описывает личный тест и хранение до `/delete`. Для приглашения других людей владелец должен определить подходящие цель, сроки хранения, контакт, резервные копии и условия участия и заменить этот текст. Политика публичного пилота здесь не утверждается.

## Протокол доставки

Используется HTTPS Bot API и long polling, без webhook и входящего сетевого порта. Адаптер предназначен только для обновлений, полученных своим клиентом Bot API. Его внутренний `handle()` нельзя публиковать как неавторизованный HTTP endpoint.

Изменения модели, квитанции GameService и исходящие действия одного обновления записываются в общей транзакции с вложенными savepoint. Сетевые вызовы выполняются только после COMMIT. Таблица `telegram_updates` хранит хеш входного обновления, очередь действий и позицию отправки. Порядок ключей JSON не влияет на распознавание дублей. После успешного завершения исходящие тексты и документы удаляются из очереди.

При сетевом сбое выполняется повтор отправки, а не повтор обучения. После перезапуска сначала отправляется сохранённая очередь, затем запрашиваются новые обновления. Смещение `getUpdates` повышается только после завершения обработки. Состояние очереди не зависит от того, сохранил ли Telegram старое обновление на своей стороне. Постоянные отказы API 400/403 считаются завершённой неуспешной отправкой; отказ доставки прогнозов/обратной связи отмечается в `telegram_deliveries`. Временные сетевые ошибки, 429 и 5xx повторяются; `retry_after` учитывается.

`telegram_deliveries` различает принятие запроса Telegram API и его отказ, фиксирует время и message_id для прогноза и обратной связи. Принятие API не доказывает прочтение пользователем. В частности, поле `visible` в математическом snapshot означает режим показа, а не подтверждение доставки. Эти источники должны анализироваться раздельно.

Гарантируется отсутствие повторного хода при дублях update/callback. Ровно однократная отправка сообщения не гарантируется: авария между ответом Telegram API и записью локального подтверждения может привести к повторной отправке или редактированию. Для callback используется редактирование существующего сообщения; «message is not modified» считается успешным повтором. Старые или чужие кнопки не могут изменить модель другого участника.

Одна БД закреплена за одним bot_id. Локальная аренда `polling_lease` предотвращает запуск двух обработчиков на той же БД; продлевается каждые 10 секунд и истекает через 120 секунд. Не запускайте разные копии БД с одним токеном. Доступ отозванного ID не восстанавливается из сохранённой очереди.

## Экспорт, удаление и резервные копии

Экспорт содержит только данные своего участника: исходные прогнозы, состояние модели, сессии, ходы, условия согласия и отметки API-доставки. Текущий скрытый ход сначала нужно завершить: его полный snapshot содержит прогноз. Размер отправляемого JSON ограничен 10 MiB; более крупный файл требует локального экспорта владельцем.

Подтверждённое `/delete` транзакционно удаляет историю, модель, сессии, квитанции, снимки, recovery_audit, связь с Telegram ID и связанные записи доставки. До согласия `/delete` также очищает служебные данные обращения. Сохраняются только номера старых обновлений без привязки к человеку, чтобы повтор старого обновления не восстановил удалённую игру. Для нового участия снова требуется `/start` и согласие.

Это логическое удаление из рабочей базы. Оно не удаляет сообщения/файлы в Telegram, отдельно скачанные экспорты, резервные копии, настроенный список доступа в `.env` и физические остатки страниц SQLite/WAL. После удаления не следует восстанавливать старую резервную копию без повторного применения удаления. Автоматической политики резервирования или гарантированного стирания носителя пока нет. Для личного теста резервную копию делают при остановленном боте, копируя всю приватную папку с файлами SQLite; не публикуйте её.

Полные снимки после каждого хода остаются ограничением прототипа: объём растёт быстро. До расширенного пилота нужны политика checkpoint/retention, проверка резервного восстановления и выбранный способ постоянного размещения.

## Проверки и исходники

`src/telegram/adapter.mjs` — команды, кнопки, права, согласие, экспорт/удаление и durable outbox. `client.mjs` — Bot API, `polling.mjs` — смещение обновлений, `lease.mjs` — блокировка обработчика, `config.mjs` — конфигурация. `scripts/telegram-bot.mjs` — запуск. Миграция `002.sql` дополняет прежнюю схему; миграция v1→v2 проверена с сохранением существующего состояния.

```powershell
node --test tests/telegram*.test.cjs
npm.cmd test
```

Тесты используют только искусственные пользователи и `source: simulated`. Проверяются: отсутствие модели до согласия, allowlist и личные чаты, чужие кнопки, дубли и одновременная обработка, ограничения слепого режима, отказ сети, восстановление очереди из файла после закрытия сервиса, откат при сбое записи outbox, экспорт, подтверждённое удаление, миграции, аренда, порядок подтверждения offset и отсутствие токена в сообщениях об ошибках. Настоящая отправка сообщений в Telegram этими тестами не выполнялась.

Контракт транспорта проверен по официальной [документации Bot API](https://core.telegram.org/bots/api), в частности [getUpdates](https://core.telegram.org/bots/api#getupdates), [CallbackQuery](https://core.telegram.org/bots/api#callbackquery), [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton), [sendDocument](https://core.telegram.org/bots/api#senddocument).

Прежняя личная история переносится административным инструментом: `HISTORY_IMPORT.md`. Текущая схема БД v3 сохраняет исходные Telegram-прогнозы отдельно от повторного обучения после импорта.
