# Локальный многопользовательский прототип — этап 2

Актуальная политика хранения `storage-preview-1` ограничивает полные снимки пятью на участника; подробности обслуживания и проверок — в `STORAGE_AND_HISTORY.md`. Ниже сохранено описание исходного прототипа и его протокола.

Дата: 2026-11-14. Версия протокола: `local-prototype-1`. Это внутренний JS API без HTTP, Telegram, внешней авторизации или публичного сбора данных. Авторизация владельца на реализацию локального этапа не означает запуск пилота.

## Запуск

Нужен Node.js >=22.13 с `node:sqlite`. В Node 22 возможен ExperimentalWarning стандартной библиотеки. Внешние зависимости отсутствуют.

```powershell
npm run demo:service
node --test tests/service.test.cjs
```

Демонстрация работает с искусственными игроками и SQLite `:memory:`. Для постоянной локальной БД создайте приватную директорию и передайте путь:

```js
import { mkdirSync } from 'node:fs';
import { GameService } from './src/service/game-service.mjs';
mkdirSync('private', { recursive: true });
const game = new GameService('private/game.sqlite');
try {
  game.createParticipant({ id: 'synthetic-a', source: 'simulated' });
  const session = game.startSession('synthetic-a', {
    requestId: 'session-1', visibility: 'blind',
  });
  const turn = game.predict('synthetic-a', {
    sessionId: session.id, requestId: 'guess-1',
  });
  // В blind до ответа prediction и p1 равны null.
  const result = game.answer('synthetic-a', {
    turnId: turn.id, bit: 1, requestId: 'answer-1',
  });
  console.log(result, game.getProgress('synthetic-a'));
} finally { game.close(); }
```

`participantId` — внутренний идентификатор, а не доказательство личности. Будущий адаптер обязан получить его из проверенной авторизации; его нельзя принимать из произвольного запроса. `getState` и `recover` — административные методы с полным состоянием модели. Их нельзя отдавать игроку, особенно в слепом режиме. Для интерфейса предназначен `getProgress` с обезличенными счётчиками и скрытым незавершённым прогнозом.

## Протокол и данные

`SqliteRepository` включает foreign keys, WAL, synchronous FULL и ожидание блокировки до 5 секунд. Начальная миграция выполняется транзакционно, версия хранится в `PRAGMA user_version`; неизвестная версия отвергается. Требуется локальная файловая система; сетевые файловые системы не поддерживаются этим прототипом.

Таблицы ядра сервиса: `participants`, `sessions`, `turns`, `predictor_snapshots`, `receipts`, `recovery_audit`. В этапе 3 добавлена миграция до схемы v2 с таблицами Telegram; подробнее — `TELEGRAM.md`. Состояние предсказателя не кэшируется между командами и всегда принадлежит одному игроку. Источник участника (`human` или `simulated`) неизменяем; в forecastLog он отображается как `live` или `simulated`. Вся демонстрация и тесты используют искусственные данные. Поле consent_version для human — техническая запись версии, а не готовая процедура информированного согласия.

Каждый прогноз фиксируется в собственной транзакции `BEGIN IMMEDIATE` до возврата вызывающей стороне. В БД сохраняется полный исходный snapshot: бинарный прогноз, P(1), вероятности и веса экспертов, признаки и время. В незавершённом ходе фактический бит отсутствует; он не входит в обучение и метрику. Возврат не доказывает, что прогноз доставлен или показан пользователю: timestamp доставки должен добавить будущий адаптер.

Ответ в одной транзакции проверяет владельца и ревизию, обучает свежий экземпляр движка на ранее зафиксированном snapshot, завершает событие, сохраняет новый снимок и квитанцию идемпотентности. Ошибка любой записи откатывает всё. После COMMIT нет отдельного изменяемого состояния в RAM, которое нужно синхронизировать с БД.

На игрока разрешены одна активная сессия и один незавершённый ход. Повтор `predict` с новым ключом во время ожидания возвращает тот же ход. Повтор ответа с тем же битом возвращает сохранённый результат; противоположный ответ получает `TURN_FINALIZED`. Ключ requestId уникален в рамках игрока сразу для всех команд: его повтор с другим типом или аргументами получает `IDEMPOTENCY_CONFLICT`. Старая квитанция остаётся первоначальным ответом, даже если ход уже завершён. При сетевом повторе клиент должен сохранять первоначальный requestId; новый ключ после завершения означает новую команду.

`startSession` завершает предыдущую активную сессию только при отсутствии ожидающего ответа. `endSession` также запрещён при незавершённом ходе. Явная сессия — метаданные протокола; математический детектор границ сессий продолжает использовать прежние временные правила. Переключение UI-сессии само по себе не сбрасывает обучение или статистику. Обратный ход часов отвергается для прогноза и ответа.

## Снимки и восстановление

В прототипе сохраняются полное начальное состояние, полный snapshot каждого прогноза и полный снимок модели после каждого ответа. Снимки защищены SHA-256; журнал ходов — контрольными суммами событий. Код предсказателя закрепляется версией и SHA-256 с нормализацией CRLF/LF в сессии. При смене алгоритма активная сессия не продолжится автоматически. Контрольные суммы обнаруживают повреждение; они не являются подписью против атакующего с правом изменения БД.

При чтении проверенных собственных снимков импортная нормализация весов не применяется повторно: исходные значения весов сохраняются побитово. Это устраняет численный дрейф при частых сохранениях и не меняет формулы движка. Legacy JSON автоматически в серверную модель не импортируется.

Повреждённый текущий снимок блокирует работу (`CORRUPT_STATE`). Явный административный `recover(id)` восстанавливает модель с начального состояния по исходным событиям. Для каждого хода повторно вычисленный прогноз должен точно совпасть с сохранённым snapshot; расхождение или испорченная контрольная сумма события прерывают восстановление. Новые прогнозы в turns не записываются и не подменяют исходные. Старый снимок, включая повреждённое содержимое, сохраняется в recovery_audit до замены. Незавершённый прогноз проверяется, но не обучает модель.

## Проверки и ограничения

Автотесты проверяют независимость игроков, слепой режим, повторную доставку, конфликт ключей и битов, владение ходом, перезапуск с ожидающим ответом, жизненный цикл сессий, проверку версии, отказ записи, явное восстановление и повреждённые события. Четыре независимых worker-обработчика с разными соединениями SQLite соревнуются за ответ; только один бит принимается. Принудительный выход worker посреди транзакции подтверждает rollback. На 100 ходах через несколько сессий полное состояние сервиса точно совпадает с непрерывно работающим ядром.

Это локальная односерверная реализация. Записи сериализуются общей блокировкой SQLite, поэтому она не рассчитана на высокую нагрузку. Полные снимки после каждого хода увеличивают расход диска примерно квадратично с длиной истории; до пилота нужна политика checkpoint/retention и резервного копирования. Сейчас нет адаптера Telegram, доставки сообщений, публичного экспорта/удаления, шифрования БД или процедуры восстановления при физическом разрушении файла. Файлы БД и WAL/SHM игнорируются Git. Временные тестовые БД содержат только искусственные данные.
