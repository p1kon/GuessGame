# Журнал инженерных решений

## 2026-11-14 — Подготовка модульного ядра

По указанию владельца продолжены этапы 0 и 1 из ROADMAP. Все изменения выполняются в инфраструктурной ветке. Эталон закреплён локальной меткой `baseline-v2.3.2` и SHA-256.

Выбраны нативные JS-модули `.mjs` без TypeScript, зависимостей и пакетного сборщика: перенос не должен одновременно менять язык, математику и инфраструктуру. Предсказатель пока остаётся одним крупным модулем для уменьшения области рефакторинга. ИНР и симулятор выделены отдельно.

Автономный HTML собирается из этих же модулей. Разметка и клиентский код имеют собственные исходники. Новая сборка маркируется `modular-preview-1` в манифесте, алгоритмические метаданные остаются 2.3.2. Полноценный новый релиз потребует отдельной версии и релизной документации.

Протокол отличий и проверок: `MODULAR_CORE.md`. Telegram-архитектура, политика пилота и публичное размещение остаются отдельными решениями.

## 2026-11-14 — Локальный GameService и SQLite

Владелец разрешил переход к многопользовательскому GameService и транзакционному хранилищу. Для этапа 2 выбраны baseline, встроенный `node:sqlite`, синхронные команды и BEGIN IMMEDIATE. Это локальный прототип, без HTTP/Telegram и публикации. Источник участника фиксируется при регистрации; демонстрация и тесты искусственные.

Для надёжного повтора введены квитанции requestId с отпечатком аргументов. Первый ответ на ход окончателен. Полные прогнозы сохраняются до ответа, полные состояния — после каждого ответа, с явным восстановлением и аудитом повреждённых снимков. Пока сохраняется полная диагностика всех экспертов; эта техническая стратегия прототипа не утверждает политику хранения публичного пилота.

При чтении собственных проверенных снимков сохраняются исходные веса, поскольку повторная нормализация legacy-импортом создаёт численный дрейф. Формулы ядра не менялись. Сравнение с непрерывным движком проходит побитово. Подробности API, проверок и ограничений — `GAME_SERVICE.md`.

## 2026-11-14 — Подготовка закрытого Telegram-теста

Владелец разрешил следующий этап и сообщил, что бот и числовой Telegram ID уже есть. Выбраны long polling, доступ по allowlist, личные чаты, видимый/слепой режимы и локальный запуск. Подготовлен игнорируемый `.env` с текстом для личного технического теста; токен и ID заполняются владельцем, не через чат.

Добавлены согласие, личный экспорт и подтверждаемое удаление; экспорт скрытого незавершённого хода блокируется. Квитанции GameService и durable outbox фиксируются атомарно через вложенные SQLite savepoint. Исходные прогнозы и результаты API-доставки хранятся раздельно. Ровно однократная отправка сообщения не заявляется. Блокировка процесса ограничивает БД одним polling-обработчиком.

Математика и автономный HTML не менялись. Схема БД обновлена до v2 с миграцией v1→v2. Проверки выполнялись на искусственном транспорте, без реального токена и отправки сообщений. Публичный набор участников и облачное размещение не запускались. Запуск и ограничения: `TELEGRAM.md`.

## 2026-11-14 — Импорт личной истории

Владелец подтвердил работоспособность бота и запросил продолжение с прежними 1200 ходами. Перед переносом обнаружены 20 завершённых Telegram-ходов, ожидающих ответов нет. Владелец остановил бота для переноса.

Выбрана миграция v2→v3: историческое состояние становится базой обучения; уже показанные Telegram-прогнозы сохраняются, а их повторное обучение хранится отдельно как replay. Счёт не заменяется контрфактическим пересчётом. До изменений выполняются SQLite-резервирование и пробный перенос на копии. Формулы ядра не меняются. Протокол: `HISTORY_IMPORT.md`.

## 2026-11-14 — Размещение личного бота на VPS

По разрешению владельца выполнен перенос на Ubuntu VPS. Выбраны официальный Node.js 26 LTS, отдельный системный пользователь, systemd, локальный диск SQLite и ежедневные проверяемые копии с хранением последних 14. Действующая база перенесена согласованным снимком, показанные прогнозы и импорт сохранены. Автозапуск проверен настоящей перезагрузкой сервера. Первая копия дополнительно сохранена вне VPS на ноутбуке и проверена восстановлением.

Регулярное независимое хранилище ещё не выбрано; автоматические серверные копии не объявляются полноценной защитой от потери VPS. Математика не менялась, пилот остаётся закрытым. Эксплуатация и оставшиеся задачи: `DEPLOYMENT.md`.

## 2026-11-14 — Общая учётная запись веб/Telegram

Владелец запросил серверную многопользовательскую веб-страницу, логин/пароль и привязку Telegram. Подтвердил временный доступ по IP и будущий домен pkonovalov.com. Выбраны собственный VPS, HTTPS с IP-сертификатом, закрытая регистрация по коду доступа, scrypt и защищённые серверные сессии.

Привязка требует одноразового кода из веб-сессии и подтверждения нужным Telegram ID в боте с отображением веб-логина. Одного ввода ID недостаточно. Обученная модель подхватывается без изменения событий; две непустые истории не объединяются автоматически. Формулы, ИНР и исходные эталонные артефакты не меняются. Детали: `WEB_ACCOUNTS.md`.

## 2026-11-14 — Публикация исходников под MIT

Владелец разрешил публикацию под MIT. Правообладатель указан как Pavel Konovalov по существующей истории Git. Лицензия относится к опубликованному коду и документации; приватные истории, секреты и базы не входят в публикацию. Проверки CI выполняются на Node.js 22 и 26.

Перед публикацией выявлена автоматическая CRLF-конверсия эталонного HTML в рабочей Windows-копии. Для эталона сохраняются исходные байты Git-коммита 9ef0c34, для остальных текстовых файлов закреплён LF. Математика и текст HTML не менялись; контрольные суммы исходников приведены к байтам Git, а прежний Windows-артефакт сохранён приватно.

## 2026-11-14 — Очистка истории и ограничение снимков

Владелец разрешил переписывание Git-истории для удаления личного JSON и оптимизацию базы. Исходные ветки/метки сохранены приватным bundle. Файл удалён из публикуемой истории стандартным git-filter-repo; force-with-lease выполнен атомарно. Закрытый PR сохраняет отдельную read-only ссылку, для которой подготовлен запрос GitHub Support.

Для модели выбраны начальный, текущий, предыдущий и два контрольных снимка через 100 ходов: максимум пять. Сокращаются только производные версии состояния, исходные события и forecasts не переписываются. Отдельный инструмент резервирует базу, проверяет факты и модели, сокращает снимки и выполняет VACUUM. Изменение формул или схемы БД не требуется. Проверки и ограничения: `STORAGE_AND_HISTORY.md`.
